# latheControl
Code for controlling a lathe's lead screw (Z-axis) with a stepper motor.

![Screen shot](https://www.martyndavis.com/wp-content/uploads/2020/10/lc.png "")

Now also will control the X-axis (cross-slide).

Allows for cutting threads, tapers, and general automated operations.

Intended to be an aid for manual machining, rather than full CNC operation.

## Getting the Code

Just `git clone <repo URL>`. Everything is in this repository: the stepper motor code (`steppermotor.*`, and the GPIO in `igpio.h`, `gpio.*` and `mockgpio.h`) used to be a separate library, [stepperControl](https://github.com/md81544/stepperControl), which was moved in at its v1.5.1, once the electronicRotaryTable program (its only other user) was replaced by gear cutting mode. That repository is kept for its history.

## Dependencies

You'll need to do the following (on deb-based systems) to install required packages:

    sudo apt install cmake libfmt-dev qt6-base-dev

on a Mac, you can use homebrew (if you've got it installed):

    brew install cmake fmt qt

The user interface uses Qt 6 (Widgets), which is available from the standard repositories on Raspberry Pi OS Bookworm or later.

## Building

To make a binary to run on non-Pi hardware, just type `make`. This mocks out the pigpio library usage, and also provides mock objects for all the steppers and rotary encoder, which means you can test it on a PC without needing to be in the workshop. This build includes debugging symbols. A serial (DRO sender) scale is simulated too, following its motor; its table has the axis's backlash compensation as its backlash, so the compensation is right, as on a machine set up well (`Axis1FakeBacklashSteps`, for the fake build only, sets a different amount: 0 for a table with no backlash, so every reversal's compensation takes the table that much further than the motor says).

To make the binary on a Pi, type `make release`. This will fail unless you're on a Pi as the pigpio headers and libraries won't be present.

To run unit tests, `make test`.

## Connecting Stepper Motors
Note that the software will take the pin high then low for each pulse to the stepper motor, so the pins you specify in the config file should be connected to the positive inputs for the stepper controller. All the negative input pins should be tied together and connected to the Pi's GND pin.

## Running, and Performance
This is designed to run on a stock Raspberry Pi 3 Model B or later: the lathe and the mill each run on a Pi 4 Model B (the mill's was a Pi 3 Model B+ until November 2026). Usage of the GPIO pins (via the pigpio library) requires root privileges, so run the program via `sudo`.

This program is very time-critical. You shouldn't need to use `nice`, as, internally, it sets the critical background (motor-related) threads to realtime scheduling.

**Note** While working on adapting the software to work with my milling machine, I installed it on a different Pi and experienced issues with motor motion. I see approximately once-per-second noticeable pre-emption of the motor threads (which are meant to be running at highest realtime priority). This exhibits as an obvious "stutter" when the carriage (either axis) is moving. After lots of investigation, I find this is related to the kernel in use. I am not sure why yet. I reverted to an older kernel, (4.19.97, which is quite old, but is the version I was running previously for the lathe) and all works OK again. I will, at some time, attempt to bisect my way up the kernel versions to see where the issue occurs. To revert to a previous kernel on the Pi, follow [these instructions](https://isahatipoglu.com/2015/09/29/how-to-upgrade-or-downgrade-raspberrypis-kernel-servoblaster-problem-raspberry-pi2/).

**Update to the above** - the problem described above does not seem to happen in more recent kernels.

**If a once-per-second stutter does appear**, a likely cause is the kernel's real-time throttling: by default, real-time threads may only use 95% of each second (`cat /proc/sys/kernel/sched_rt_runtime_us` shows `950000`), and a motor thread busy-waiting between steps during a long move can hit that limit, at which point it is paused for the remaining ~50ms. Whether this happens depends on the kernel version and configuration, which would fit the behaviour above. To test the theory, disable throttling with `sudo sysctl kernel.sched_rt_runtime_us=-1` (this lasts until reboot; the Pi has enough cores for this to be safe here) and see whether the stutter goes away. Motor threads sleep when their motor is idle, so this can only affect a motor while it is moving.

## Usage
*Note: the axes are referred to as Z and X here, but these names are configurable. Z is the primary axis (axis1) and X is the secondary (axis2).*

**Starting up** - each axis moves a little at start-up, in its positive direction, by its backlash setting (`Axis1BacklashCompensationSteps` and `Axis2BacklashCompensationSteps`), so that the slack is known to be taken up. Then its position is set to zero. Make sure the tool isn't touching the work when starting.

**Taking up the backlash slowly** (optional; `Axis1BacklashTakeUpSpeed` and `Axis2BacklashTakeUpSpeed`, in mm/min, or degrees/min for a rotary axis; on for the mill's X, at 100 mm/min) - when an axis reverses, the motor first turns through the backlash before the leadscrew's nut picks up the load. Normally that happens at the move's speed, so on a fast move the nut picks up the load suddenly (you may hear a "clunk"), and the motor can stall. With this set, a move takes up the backlash at that speed (or its own, if slower), then speeds up from rest as usual. This applies to every move (jogs, rapids, go-tos and multi-pass returns), but not while threading, or to X following Z on a taper. Tried on the mill: X used to stall on about one reversal in six; with the take-up at 100 mm/min, 40 multi-pass passes ran without a stall.

**Deceleration ramping** (optional; `Axis1DecelerationRamping = true`, and the same for Axis2; on for the mill's X) - every move slows down before it stops, to the speed its ramp starts at (40% of the motor's maximum, `Axis1MaxMotorRpm`: 400 mm/min on the mill's X), rather than stopping dead from full speed: going to a position or memory slot, fast returns, multi-pass returns, and nudges, and jogs and rapids when you stop them (see **movement**, below). It slows down at the same rate as it speeds up (`Axis1RampingSpeed`), unless `Axis1DecelerationRampingSpeed` is set (up to 100, the quickest). Stopping dead from full speed carried the mill's X on by about 0.1 mm each time, so its position drifted from its scale by a few mm over 40 multi-pass passes; stopping from 400 mm/min doesn't. So a rapid runs on after it's let go: on the mill's X, about 3.3 mm from full speed (800 mm/min), or about 1.8 mm with `Axis1DecelerationRampingSpeed = 100`. `Space` still stops everything at once. Not while threading, or for X following Z on a taper. (Only with `Axis1RampingSpeed` above zero.) Tried on the mill: with it, a large set of multi-pass passes at full speed ran without any drift, and a released rapid's slowing down is easy to manage when getting close to a position.

**The menu** - press `Tab` or `F1` (or, on the gamepad, the previous and next memory slot buttons together; see `JoystickMenuChord` in lc.cfg) to open a menu of everything you can do, with each command's keyboard shortcut alongside. Use the arrow keys (or the gamepad's D-pad, and its Enter button) to move around it (`Up` from the top goes round to the bottom, and `Down` from the bottom to the top), `Enter` or `Right` to choose, `Left` or `Esc` to go back, and `Tab` again to close it. Categories, and the less frequent commands, have a hotkey letter (shown yellow and underlined): for example `Tab`, `M`, `T` for Modes, Threading. While the menu is open, letters typed are only menu hotkeys, not their usual shortcuts. The menu doesn't stop anything: motors keep running while it's open, `Space` still stops all motors, and rapids (`Alt` + arrow) still work. Commands which can't be used at the moment (e.g. moving a locked axis, or going to, returning to or clearing an empty memory slot) are greyed out, here and in the hints shown after an axis key, and `Up` and `Down` skip over them.

**Leader key hints** - if you pause for half a second after pressing a leader key (`Z`, `X` or `\`), a panel lists the keys which can follow it, and what each does. If you type the whole shortcut quickly, it doesn't appear. `Esc` after a leader key cancels it, and does nothing else.

For general **movement** of the carriages, use the arrow keys. Press the same key again (or spacebar) to stop. Pressing `Alt` with an arrow key sets the carriage moving at its maximum speed (useful for moving tools out of the way, not actual cutting), for as long as both are held. With deceleration ramping (above), letting go, or pressing an arrow key again to stop a move, slows the axis down to a stop rather than stopping it dead, so it runs on a little (pressing the key once more while it slows down stops it at once). `Space` always stops everything at once.

Control **speed of motion** with number keys. `1`-`5` controls Z and `6`-`0` controls X. For finer control of speed, use the `-` and `+` (or `=`) keys for the Z axis, and use the leader `X` with the same keys for the X axis (for example, press `X`, then `-`).

"**Nudging**" the axes can be achieved with the `W`, `A`, `S`, and `D` keys. Each "nudge" is 0.05mm. To move less (0.01mm), press `shift` plus a nudge key. To move more (0.1mm), press `Alt` plus a nudge key. Each goes the same way as its arrow key (`W` as up, `A` as left, `S` as down, `D` as right). (Until 20 Nov 2026, the mill's rotary table turned the opposite way for `W` and `S` to its arrow keys.) If you're pressing these keys a lot, look at relative motion (below) instead.

There are six **memory locations**, you can select which one is active by means of the `[` and `]` keys. Press `M` to store the current X and Z position in the current memory slot.

Axis "**leader keys**" can be used to store just the X or Z value, for example, pressing `XM` (x followed by m) will memorise just the X value.

To **return to a position**, select the memory slot with `[` or `]` and press `ENTER`. This defaults to the Z axis unless you provide a "leader" key. For example. pressing `X`, then `ENTER` will move to the stored X value.

To move to an **absolute position**, press leader + `G` (for "go to") - for example, `ZG` will open a dialog asking for a value for Z to go to.

**Relative motion** can be performed by pressing leader + `R` - for example `XR` will open a dialog asking for an offset for X to go to. Once a relative motion has occurred, it can be repeated by simply pressing `.`

**Zeroing** - press `XZ` or `ZZ` to zero the axis at the current position. The "axis leader" key `\` (backslash) selects both axes, so `\z` will zero out both axes at once, and any axes moved by hand too (the mill's Y and Z; below).

**Setting a position** - press "axis leader" then `S` - for example `ZS` - then enter a value to change what the current position is. With the X axis, you can enter the value as a **diameter value** by also pressing `D` (which ticks the "set as diameter" option) before `ENTER`. This sets the X value to half of the diameter and displays the actual diameter in the status line at the bottom of the screen. Once a diameter has been set, the **surface speed** (Vc, in m/min) is also shown, beside the spindle speed. Both last until X is zeroed, or its position is set again (other than as a diameter).

**Halving** (to find a centre) - press "axis leader" then `H` - for example `XH` - to set the axis's position to half what it is now. Zero it with the tool (or edge finder) on one edge, move to the other edge, and halve it: zero is then halfway between them, as on a DRO. On a motorised axis, as for setting its position, its memory slots are cleared (and a dialog asks before clearing the current feature). It can't be done while the axis is moving.

**Axes moved by hand** (optional; `Axis3Kind` and `Axis4Kind`, the mill's Y and Z) - an axis with no motor, whose position is read from its scale (on the mill, from the DRO sender, as X's is), is shown on a line of its own below the motorised axes, as on a DRO. Its leader key (`Y` or `Z` on the mill) then `Z` zeroes it, `S` sets its position, and `H` halves it (above); `\z` zeroes it along with all the other axes. Nothing moves it, so there are no nudges for it, but it's in the **memory slots**: `M` stores every axis, its leader then `M` stores it alone, and its leader then `Delete` clears it (as `Delete` does every axis). Its leader then `Enter` **goes to its slot**: you wind the handle, and its line shows the distance to go (e.g. "to 12.50: 0.34 to go", in red if you've gone past). Once the reading has settled within two counts of the target, it's done. Nothing blocks meanwhile, and `Space` or `Esc` cancels it. `\` then `Enter` goes to the slot on every axis at once: the motors move while you wind, except for an axis with `Axis3InSlotGoTo = false` (the mill's Z, which is never moved while X is). Zeroing, setting or halving it clears its memory slots, as for the motorised axes. It starts at zero, wherever it is. Its zero isn't kept when the program stops, nor if the scale's readings are lost (e.g. the DRO sender was switched off, which starts its count again): it shows "no reading" until they return, and then starts at zero again. Tried on the mill (19 Nov 2026): zeroing, alone and with `\z`. Check each scale counts the right way: the mill's Y needed `Axis3ScaleReversed = true`.

**Current feature** (lathe; `CurrentFeature` in lc.cfg) - the program remembers the diameter of the surface you're working on and the Z of the work's end, shown in a "Current feature" box. Unlike the diameter in the status line, the feature's diameter doesn't change as X moves. Setting X as a diameter (above) records it, as the tool is on the surface you've just measured; `XD` records the diameter at the tool again at any time (X must have been set as a diameter). After facing, `ZE` marks Z here as the work's end: the free end of the work, not a shoulder part way along. Both are also in the menu, under Feature, along with clearing them. They're kept for this session only, and each goes when its axis's position does: a re-zero, a motor fault, or setting the position (unless adjusting); the diameter also goes when X is no longer set as a diameter. Before a re-zero or a position set would clear any of it, a dialog asks first (`Enter` or `Y` to go ahead, `Esc` or `N` to cancel). Setting X as a diameter doesn't ask, as it replaces the diameter with the one just measured. A multi-pass which cuts from the work's end sets the diameter to the one it finished at. The menu's Feature category can also go back to it: to its start (X on the surface and Z at the work's end, either exactly or clear of it by `FeatureStartClearance`, away from the chuck as set by `Axis1TowardsChuck`), with X retracting before Z moves and coming in after; X alone to the surface; or Z alone to the work's end (exactly or clear of it), which is refused if X is deeper into the work than the feature's surface. Not while threading, tapering or during a multi-pass.

**Tool library** (lathe; `ToolLibrary` in lc.cfg; tried on the machine with two tools, which changed back and forth repeatably) - the program keeps a library of the tools you use in the quick-change toolpost, each with its offsets from the reference tool (tool 1, e.g. the right-hand turning tool used most of the time), and its nose radius. The tool in use is shown in a "Tool" box at the top right. Changing tool (`T`, or the menu's Tool library, `T` in the menu) asks which tool is now in the toolpost, then shifts the Z and X positions by the difference between the two tools' offsets: nothing moves, but the positions now read where the new tool's tip is. So memory slots, the current feature, a multi-pass's start and so on stay where they were on the work, and X stays measured from the centre if it was set as a diameter. Changing to a tool and back again comes back to exactly the same positions. Not while anything's moving, during a multi-pass, or in a mode other than multi-pass or radius. The list ends with **T? Unknown tool**, for a tool that isn't in the library (e.g. one not measured yet, or a knurling tool), shown as a yellow `T?`. Its offsets aren't known, so nothing shifts: the positions still read the last tool's tip, as the box shows ("positions: T1"), and changing back to a tool in the library shifts from that tool, so nothing set on the work is lost. But zeroing an axis or setting its position with the unknown tool makes that axis's positions the unknown tool's, which can't be shifted to another tool's: changing to a tool in the library then leaves that axis's position as it is, and clears what was set on the work along it (the work's end for Z; the diameter, and X being measured from the centre, for X), asking first if that's part of the current feature. Tools are measured from one in the library, so not while the unknown tool is in use. **Defining a new tool** (Tool library, New) measures its offsets from the tool in use, by touching the same two surfaces with each: the work's outside diameter, and its end. Only external tools (e.g. turning, facing or chamfering tools) can be measured so far; not boring bars, which can't reach the outside diameter (and with X's retraction set for boring, it's refused). With the tool in use, touch the diameter (just a scratch, e.g. under a magnifier) and press `Enter`, then touch the end and press `Enter`; change to the new tool, and do the same. Each diameter touch must be made with X moving in, and each end touch with Z moving towards the chuck (`Axis1TowardsChuck`), so that the backlash is taken up the same way each time: if not, the touch is refused, and you back off and come in again. Meanwhile, the axes can be moved as usual, but nothing else can be done; the steps are shown on screen, and `Esc` cancels. Once the last touch is in, the program asks for the tool's description and nose radius, stores it, and makes it the tool in use. **Measure a tool again** does the same for a tool already in the library (e.g. after changing its insert); measuring tool 1 again, from another tool, moves every tool's offsets so they're from tool 1's new tip. **Describe the current tool** changes its description and nose radius (e.g. tool 1's, which is never measured). The radius dialogs start with the current tool's nose radius. The offsets only hold while the toolpost isn't rotated on the carriage: moving it without rotating it moves every tool by the same amount, so their offsets from each other stay the same (though the positions set on the work don't). The library is kept in `ToolLibraryFile` (tools.cfg unless set), which the program writes each time it changes, keeping the one before as tools.cfg.bak; it's plain text, so it can be edited while the program isn't running.

**Limit switches** (optional; `LimitSwitchPin` in lc.cfg) - any limit switch stops all the motors at once, and ends whatever was running (e.g. a multi-pass). A message flashes, and a dialog opens: until you clear the stop (`Enter` or `Y` in the dialog, or later from the menu, under System), nothing will move, and only keys which don't move anything work (`Space`, `Esc`, `U`, quitting). This is so that, for example, repeated nudges into a switch can't go unnoticed. Once cleared, move off the switch carefully: all the switches share one pin, so the program can't tell which one it is, and won't stop you moving further into it. While a switch is still pressed, the message says so; it stops the motors again only after it has been released and pressed again. Normally-closed switches wired in series are recommended (see lc.cfg), so that a broken wire or an unplugged socket stops the motors too. The position isn't lost, so nothing needs re-zeroing.

**Linear scale** (optional; `Axis1Scale` in lc.cfg) - with a scale on axis 1 (the lathe's Z, read from its quadrature output, or the mill's X, read from its DRO sender through a USB-serial adapter), the scale's position is shown on the axis's row, after its speed, with how far it is from the motor's position in brackets, e.g. "scale 12.345 (+0.010)". A difference which grows as you work means lost steps (or a wrong backlash setting). The scale is lined up with the motor (its difference made zero) once its reading has settled at the start, and again when the axis is zeroed or its position set, and when its readings return after being lost (e.g. the DRO sender was switched off). Until then it shows "settling" or "no reading". Each time the axis stops, lc.log records the difference once the reading has settled, and how long that took.

**A scale on axis 2** (optional; `Axis2Scale`, and the same keys as axis 1's with `Axis2` in place of `Axis1`; planned for the lathe's X, read from its quadrature output as Z's is, and not yet tried on a machine) - axis 2's scale does everything axis 1's does, below: it's shown on its row, lined up, re-based at rest (`Axis2ScaleRebase`), checked against the motor at rest and while moving, re-based by hand (axis 2's leader then `B`, e.g. `XB` on the lathe), and finishes positioning moves (`Axis2ScaleFinishMoves`, with its own on and off in the menu's System category, `G`). **Between a multi-pass's passes** (`Axis2ScaleRebaseBetweenPasses`): axis 2 is the feed axis (the lathe's X), so after each feed to a pass's depth, the pass waits for its scale to settle ("Waiting for X's scale", as for axis 1's), re-bases it, and if that shows X short of (or past) the depth, feeds again, so every pass is cut at the depth the scale says. After three such feeds without getting there, the passes stop with a warning, rather than cut at the wrong depth. While paused, X is re-based each time its reading settles (and by hand with `XB`), and unretracting and the next feed then go from the corrected position. A quadrature scale on axis 2 must have its pins set (`Axis2ScaleGpioPinA` and `Axis2ScaleGpioPinB`): axis 1's default to GPIO 5 and 6, which the two would otherwise share. With a scale on axis 2, the taper's angle and "RETRACTED" are drawn a line lower, to make room. If both axes disagree with their scales at once, one dialog asks about both (see **Relying on the scale**, below).

**Re-basing from the scale by hand** (with a scale on axis 1) - axis 1's leader then `B` (`XB` on the mill; also in the menu, under Position) sets the axis's position to the scale's, at any time: nothing moves, and the difference shown on its row goes to zero. Memory slots and the current feature stay where they are on the work, as only the motor's idea of where it is changes. Use it when the difference has grown (e.g. after a stall), without waiting for a move or the mismatch dialog. Only when the axis has stopped and the scale's reading has settled (otherwise it says why), and not during a multi-pass (except while one, or gear cutting, is paused between passes: the next pass moves to its start from the corrected position), a nudge or other short sequence, a finishing move, a backlash measurement, or the lathe's modes (threading, tapers and so on). lc.log records the change ("re-based by hand").

**Relying on the scale** (optional; `Axis1ScaleRebase` and `Axis1ScaleWarnMm`, on for the mill) - each time the axis stops and the scale's reading has settled (about 2 seconds on the mill), the position shown is set from the scale's (nothing moves). So the position, and every move, memory and go-to made from it, follows where the table really is, whatever the backlash. While moving, the position shown is still the motor's, so it can change by a count or two when the reading settles. At rest, the scale is still watched: if its reading changes by two counts or more (e.g. the table was pushed by a cut, or knocked), the position follows it once it has settled again. It isn't done part way through a multi-pass, nor in threading, taper and the other lathe modes. **Between a multi-pass's passes** (optional; `Axis1ScaleRebaseBetweenPasses`, on for the mill): in a multi-pass or gear cutting, before each cut, it waits for the scale's reading to settle after the return ("Waiting for X's scale to settle", in a box over the display, which goes by itself: about 2 seconds a pass on the mill; keys other than Space do nothing meanwhile), sets the position from the scale's, and moves the axis to the pass's start from there. So a drift or a few lost steps don't build up from pass to pass, with or without pauses, and if the scale and motor are too far apart, everything stops at the next pass rather than only at the end. While paused, the position is also set from the scale's each time the reading settles. `Space` stops it as usual. Not for threading, knurling or a radius. If the scale and the motor are further apart than `Axis1ScaleWarnMm` (0.2 mm on the mill), something's wrong (e.g. the motor stalled and lost steps), so everything stops, and a dialog asks which to believe. With scales on both axes, if both disagree, one dialog asks about both: it waits for the other axis's scale to settle first (the first mismatch stops everything, and the other axis stops a moment later), lists each axis's disagreement, and `Y` or `N` applies to both. An axis whose scale is misreading keeps its motor's position, whichever you choose. (Except when the table has gone *further* than the motor, the way it was moving: stopped dead from speed, it carries on into the slack, so the backlash setting is allowed on top in that direction. A stall leaves the table behind, so is still caught.) In the dialog, `Y` or `Enter` to use the scale's position (usually right after a stall), `N` or `Esc` to keep the position shown and line the scale up with it again. Nothing can move until it's answered. The scale's position is only ever used once its reading has settled properly: if it's still jumping about, the dialog says so, and `Y` waits until it settles and asks again (on the mill once, with the lathe running, the reading jumped by hundreds of mm at a time for half an hour). The re-basing above, and finishing moves on the scale (below), likewise only use a reading which has settled. **A misreading scale** (optional; `Axis1ScaleFaultMm`, 5 mm on the mill): with the axis at rest, the motor holds the table, so a jump in the reading of more than that can't be the table moving. Everything stops at once, and a dialog says the scale is misreading (e.g. interference, or a loose connection): any key keeps the position shown and lines the scale up with it again.

**While moving** (optional; `Axis1ScaleStallMm`, `Axis1ScaleMovingFaultMm` and `Axis1ScaleLagMs`, on for the mill) - the scale is watched during moves too, allowing for its reading lagging the table (on the mill, the sender's reading trails the table by about 0.2 seconds' worth of movement). If the table falls further behind the motor than `Axis1ScaleStallMm` (3 mm on the mill), the motor has stalled: everything stops at once ("X stalled ... stopped"), rather than carrying on to the end of the move, and once the reading has settled, the dialog above asks which to believe (usually the scale). If the reading changes faster than the table could move, or gets further ahead of the motor than `Axis1ScaleMovingFaultMm` (the table can't outrun its motor), the scale is misreading, and it's dealt with as a misread at rest. Allowing for that lag, a 3 mm stall at full speed shows after about a third of a second.

**Finishing moves on the scale** (optional; `Axis1ScaleFinishMoves`, on for the mill) - a positioning move (going to a memory slot, a typed position, a relative move, or the last position with `L`) finishes on the scale: once it has stopped and the reading has settled, if the table is more than a count from the target, a small correction move takes it there, approaching the same way as the move did. If it went past, it backs off past the backlash (at least 0.5 mm) and approaches again, so it never pushes back the other way, e.g. into a pocket's end wall. That adds about 2 seconds or more to each such move; the status line says "Finishing on the scale" meanwhile, keys wait until it's done (as for a nudge), and `Space` stops it. After three corrections it gives up with a warning. Not for jogs, nudges or fast returns, nor during a multi-pass. The menu's System category turns it on and off ("Finishing on the scale is ON"), e.g. to save the wait at each end of a cut.

**Approaching on the scale** (optional; `Axis1ScaleApproachMm` and `Axis1ScaleApproachSpeed`, and the same for Axis2; on for the mill's X, at 0.2 mm and 20 mm/min, not yet tried there) - a move finished on the scale stops this far short of its target, waits for the reading to settle, then creeps the rest at this speed, the same way. A correction afterwards can't undo an overshoot if the tool is in the work (e.g. at a pocket's end wall), and the table can go further than the motor says: stopping from speed, it carries on into the slack, and on a reversal, the backlash compensation is a fixed amount where the real backlash varies along the table (0.31-0.45 mm on the mill's X). Creeping the last of it in the same direction means it never reverses, has next to no momentum, and leaves the slack taken up the way the tool goes into the work. A move shorter than the approach creeps all the way. Backing off after going past comes back to the approach's start, and creeps from there. It adds one more wait for the scale to each such move. The speed is put back afterwards (as a stop from it would leave it: e.g. a fast go-to still ends at `Axis1SpeedResetTo`). With a scale on axis 2 and `Axis2ScaleRebaseBetweenPasses`, a multi-pass's feed to each pass's depth approaches the same way: it stops short, waits for the scale and re-bases, then creeps in, so X never goes deeper than the pass; if it's past the depth (e.g. fed again after a re-base), it backs off past the backlash and comes in again, rather than reversing onto it. With `Axis1ScaleRebaseBetweenPasses` too (as on the mill), a multi-pass's (or gear cutting's) moves of the cut axis approach the same way: each cut stops short of its end (e.g. a shoulder, or a pocket's wall), waits for the scale and re-bases, then creeps to the end; and the return, the cut back, and the move to a pass's start do the same at the start (so both walls of a pocket are safe). The reversal into each cut is where the backlash compensation can shift the whole cut, and this catches it before the end. The cost is a short dwell with the tool in the work, the approach's distance before the end (about 0.5 seconds on the lathe's Z, 2 on the mill's X), which may leave a faint mark there; and each pass waits for the scale twice (at the cut's end and the return's), rather than once before the cut. The creep is never faster than the cut was going. Not for a radius's path, threading, or a cut with X following Z (a taper correction), where re-basing Z part way would move X.

**Measuring the backlash** (with a linear scale on axis 1, e.g. the mill's X) - the menu's System category has "Measure Z's backlash (with its scale)" (`Tab`, `Y`, `B`). After a dialog warns that Z is about to move (make sure the tool is clear of the work), Z moves back and forth by 1 mm (or twice its backlash setting, if that's more), starting away from the chuck, and ends where it started, which takes about 20 seconds. After each reversal it compares how far the axis moved, by the scale, with how far it should have. Any shortfall is backlash which `Axis1BacklashCompensationSteps` doesn't cover (or, if it went further, the setting is too large). A dialog then gives the backlash in mm and in steps, to put in the config file, and how much the measurements varied (if by more than a few counts of the scale, measure again). Nothing else can move meanwhile, and `Space` stops it.

**Sounds** (optional; `SoundAlert` and `SoundAlarm` in lc.cfg, on for both machines) - the program plays a sound through the monitor's HDMI speakers when it needs your attention. The alert (`sounds/alert.wav`) means it's waiting for you: a multi-pass (threading, turning, knurling, a radius or gear cutting) has paused between passes, finished, or arrived at its start. The alarm (`sounds/alarm.wav`) means something has gone wrong: a motor's driver has gone into alarm, a limit switch has been pressed, the scale disagrees with the motor, or a warning has appeared by itself (e.g. a multi-pass stopped, or the spindle is too fast for the thread). The alert is also played once when the program starts, as the first sound after the Pi boots is always lost: this one wakes the sound output, so the later ones are heard. A warning which answers a key you pressed (e.g. "Stop the motors first") has no sound, nor do the dialogs you open, and the same warning sounds at most once every 10 seconds. The sound is played with `aplay` (`SoundPlayer` to change it), as the user who ran `sudo`, so that it reaches their desktop's sound server (PipeWire). Raspberry Pi OS turns the HDMI sound output off after about 10 seconds of quiet, and the start of the next sound can then be lost while it wakes up. To keep it on (tried on the lathe: a sound after 30 minutes' quiet played in full), create `~/.config/wireplumber/main.lua.d/51-disable-suspension.lua` containing:

    rule = {
      matches = {
        { { "node.name", "matches", "alsa_output.*" } },
      },
      apply_properties = {
        ["session.suspend-timeout-seconds"] = 0,
      },
    }
    table.insert(alsa_monitor.rules, rule)

then run `systemctl --user restart wireplumber`. (This is for WirePlumber 0.4, as on Bookworm: later versions use a different format.)

**Retraction** - `R` retracts the X axis by `Axis2RetractionDistance` in lc.cfg (2 mm unless set; of X travel, not on the diameter). Press again to unretract. Retraction can be inwards for boring operations, see "Special functions" below. When boring a small hole, check that the back of the boring bar has room for it. A multi-pass (and threading passes) retracts differently: just clear of where it started, see below.

**Locking an axis** - `ZK` or `XK` locks the axis in software, or unlocks it again; locked, its label is grey. Use it when the axis is locked physically (e.g. the cross-slide's lock), so that nothing tries to drive the stepper against the lock: X's open-loop stepper would lose its position without anything noticing. Nothing moves a locked axis: not the keys, memory returns, fast returns, retracts (including `ThreadingAutoRetract`), the current feature's go-tos, or a multi-pass. Each is refused, with a message to unlock it first. In a taper, X follows Z, so Z doesn't move while X is locked either. An axis can't be locked while it's moving, or while a multi-pass is cutting; one that's paused can be, and doesn't carry on until it's unlocked.

**Fast return** - pressing `Z` then `F` will rapidly return the Z axis to the current memory slot (`X` then `F` for the X axis; `\` then `F` for both).

**Last Position** This is **EXPERIMENTAL** - press `L` to return the Z axis (only) to its last position. This works with multiple positions, so if you go from 0.0mm to, say, 5.0mm then 7.0mm, pressing `L` once will return to 5.0mm, and pressing it again will return to 0.0mm. If there are no positions in the stack then pressing `L` does nothing.

**Inches** - press `U` to switch the display between mm and inches (also in the menu, under System). In inches, positions are shown to four decimal places, feeds in in/min and the surface speed in SFM, and values you type into dialogs (e.g. go to, offset, set position) are in inches too: each dialog says which units it expects. Axes measured in degrees (e.g. a rotary table) aren't affected. Everything is still metric internally, and the program always starts in mm.

**Quit** - press `Ctrl`+`Q` to exit the application.

**Shutdown** - press shift and `*` (asterisk) to shutdown the computer (prior to power down)

### Special functions
Open the menu's Modes (`Tab` then `M`) and press one of the following. Modes which make no sense on a machine can be left out with `DisabledModes` in its config: lc_mill.cfg leaves out threading, tapers, the quick chamfer and knurling, whose keys then do nothing either.
* `T` - threading: choose a type of thread (e.g. metric coarse, BSW), then a size, and press `M` for male (external) or female (internal). The dialog shows the diameter to turn or bore, and the depth to cut, with a diagram of the profile; female threads also set X to retract inwards. The sizes come from `threadpitches.cfg` (or the file set by `ThreadsFile` in lc.cfg), which can be edited to add more: see the comments at its top. In this mode, each Z move (e.g. to a memory slot) is a threading pass, with Z locked to the spindle's position as if geared to it: it moves the pitch for every revolution, from its start, however the spindle's speed varies. Every pass starts at the same angle of the spindle, so passes follow the same thread. (This needs a whole number of encoder pulses per spindle revolution; `RotaryEncoderPulsesPerRev` x the gearing.) With `ThreadingAutoRetract`, X retracts at the end of a cut and comes back in at the end of the return. The menu's Modes turns this on and off ("Auto-retract is ON" or "OFF"): `A` toggles it, and the menu stays open so you can see which way it's now set; `Enter` closes the menu. It starts as the config says and isn't saved, and the threading display shows whether it's on: e.g. turn it off while X is locked, rather than having each pass warn that X is locked. If the spindle speeds up beyond what Z can follow, the pass stops with a warning.
  **Threading passes** (**EXPERIMENTAL**; `Tab`, `M`, `N` in threading mode) cut the thread pass by pass, as a multi-pass (below) does: the same dialog, with X's infeed starting at the thread's depth (for a new thread; otherwise as last time) and the step-over being the infeed per pass. X always retracts between passes, as the return isn't locked to the spindle: to `MultiPassRetractClearance` beyond the start (where the tool touched the work, so also where the thread's crests are), as a multi-pass does. For a female thread, this keeps the boring bar from moving across the bore by a fixed 2 mm. Spring passes retract to the same place. Then `Enter` moves to the start, and `Enter` again starts the passes: each is a threading pass, locked to the spindle and starting at the same angle; X retracts, Z returns at full speed, and X comes back in and feeds in for the next. Pausing, nudging X while paused, and `Enter` during a pass to pause after it all work as for a multi-pass. Once the passes have finished, `Enter` takes a **spring pass** at the same depth and pauses: nudge X in first if you like (`W`/`S`, or `Shift` for the fine nudge; not the `Alt` nudges, as releasing `Alt` stops everything), and `Enter` takes another, until the nut fits; `Space` ends them. To try the nut on, move the tool out of the way: between spring passes, X can be moved out (`S`/`s`) and Z along (`Left`/`Right`, locked to the spindle as any Z move in threading mode is; again, or `Space`, to stop); or press `Space` first to end them, after which anything goes (e.g. retracting with `R`). `Enter` first moves back to the start of the last pass, at its depth (saying "Stop the motors first" if Z is still moving), and `Enter` again takes the pass. (Stay in threading mode meanwhile: leaving it ends the spring passes. Z only moves by key in threading mode with the spindle running, but the move back doesn't need it to be.) X deeper than the last pass (nudged in) is taken as meant, and the pass is cut there; X shallower (moved out) always goes back first, even while paused. To run all the passes again, set them up again from the menu. Two more options in the dialog are on unless turned off (they're remembered): **constant area** (`A`) makes each pass remove about the same area, so the passes get shallower as they go deeper (what you type is then the first pass's infeed; pass n goes in to that times the square root of n, but at least `ThreadingMinimumInfeed`, 0.02 mm, further than the pass before), and **compound infeed** (`C`) moves each pass's start along Z by its depth times tan 29.5° (for a 60° thread; Whitworth's is 27°), as a topslide set over would, so only the leading flank cuts. With the compound infeed, the start moves the way the cut goes, by up to about 0.57 of the depth (the dialog says how far), so start at least that far off the work. The cut's end doesn't move. `ThreadingAutoRetract` isn't used meanwhile. If the encoder loses pulses during the passes (see the threading warning above), every later pass would cut a slightly different thread, so they stop: during a cut, once it's finished and Z has returned, with X left retracted (stopping part way would leave the tool cutting a ring in the thread). Neither the passes nor spring passes will start again on that thread; choosing the thread again (e.g. for new work) clears it. While they're set up, `Enter` runs them rather than going to the memory slot (`ZEnter` still does); choosing a thread again, or leaving threading mode, goes back to passes by hand
* `P` - tapering: choose a preset (Morse tapers MT0-MT6, 45 and 30 degree chamfers) or type an angle, and press `I` to choose whether the tool moves in or out as it approaches the chuck. A diagram shows the tool's path (exaggerated for small angles). Presets are in `tapers.h`
* `R` - set retract mode (retract might need to be inwards rather than outwards if you're boring a hole). The direction at start-up is set by `Axis2RetractionDirection` in lc.cfg
* `O` - a radius on the work's end (tried on the machine in aluminium, with good results; only with `CurrentFeature`): a convex radius on the corner of the end, from a small one up to a full ball end. It starts from the current feature, so first face the end and mark it (`ZE`), and set X as a diameter on the work (with an outwards retraction, as it's on the outside). The dialog asks for the **radius** (at most half the diameter, which is a full ball end), the **depth per pass**, and the tool's **nose radius** (0 for a sharp tool), and shows how many passes that takes. The nose radius assumes the tool was touched off on the diameter and the end face, as a right-hand turning tool is; without it, a 0.4 mm nose would leave the radius about 0.17 mm proud at 45°. `Enter` moves to the start (X retracts first; then Z just off the end, by `FeatureStartClearance`, and X on the diameter), and `Enter` again starts. Each pass is an arc about the finished radius's centre: the first is the largest that still touches the corner (taking off no more than the depth per pass), and each after is the depth per pass smaller, down to the radius, so every pass removes about the same depth. Each runs from the end face round to the diameter, so the first passes are short, nearly straight cuts across the corner. X steps in to the pass's start (off the end), Z moves on to the end face, then the arc is cut as a series of short tapers (each within 0.005 mm of the arc), Z moving towards the chuck and X outwards, and Z returns at full speed along the diameter, which is clear of the work by then. Where the arc is steep (near the end face), X has to move many times as fast as Z, so Z slows down there to keep X within the speed it can start at without ramping: a lagging X would cut too deep. Each cut is at the Z speed set (or slower, there), which you can change during the cut, for the rest. `Enter` during a pass pauses once it's done, and `Space` stops everything. The display shows each pass's radius, down to the finished one
* `F` - a filleted shoulder (**EXPERIMENTAL**; tried on the machine with a 2 mm fillet and a sharp tool, with good results; only with `CurrentFeature`): turns a step down from the work's diameter, with a concave radius (a fillet) in the corner where the smaller diameter meets the shoulder. The fillet is material that's left rather than taken off, so it can't be added to a shoulder that's already square: the step is turned with it. As for a radius on the end, first face the end and mark it (`ZE`), and set X as a diameter on the work, which is the diameter the step is turned down from (with an outwards retraction). The dialog asks for the **finished diameter**, the **length to the shoulder** (from the end face, in Z's units; the dialog shows where that puts the shoulder), the **fillet radius** (at most the step's height, and at most the length), the **depth per pass**, and the tool's **nose radius** (0 for a sharp tool; at most the fillet's radius), and shows how many passes that takes. The tool must be able to face the shoulder, as it goes up the face at the end (e.g. a 93° or 95° approach angle; a 45° or 60° tool would rub). `Enter` moves to the start (off the end, on the diameter), and `Enter` again starts. First come straight passes, each from off the end: down to the height of the fillet's top, right up to the shoulder, then down to the finished diameter, stopping the fillet's radius short of the shoulder. That leaves a square block in the corner, which the remaining passes cut as arcs about the block's corner nearest the end, growing by the depth per pass up to the fillet's radius, so each takes off about the same depth. Each arc starts from just short of the block (Z goes there at full speed, rather than feeding from the end), moves on to it, then is cut as a series of short tapers, as for a radius on the end, from the block's side round to its top: Z moves towards the chuck and X outwards, and near the shoulder, where the arc is steep, Z slows so that X keeps up. With a nose radius, the last pass ends by moving X alone (at X's speed) up the shoulder's face to the fillet's top, taking off what the nose left in the corner there. Each pass returns along the height it ended at, which is clear. Once finished, the feature's diameter is the finished diameter. `Enter` during a pass pauses once it's done, and `Space` stops everything. The display shows each straight pass's diameter, and each arc's radius
* `M` - multi-pass (**EXPERIMENTAL**): repeated cuts along Z, stepping X over between them. First store the start of the cut (Z and X) in Mem 1, and the end in Mem 2. Enter the X step-over per pass, and optionally press `P` to pause between passes and/or `R` to retract X before each return. Each retract is to `MultiPassRetractClearance` (0.25 mm unless set) beyond the start, where the tool touched the work, rather than a fixed distance: that's clear of the work however deep the passes have gone, and in a bore, the back of the boring bar only comes that much nearer the far side than it was when you touched off. (So does the retract before moving to the start.) `R` cycles through No, Every pass, and Last 2 passes: the roughing passes then return without retracting, which is quicker, and only the finishing ones retract, so they don't leave a spiral. (How many is `MultiPassRetractLastPasses` in lc.cfg. With a step-over of zero, every pass retracts.) Then go to Mem 1 (e.g. `ZEnter` and `XEnter`) and press `Enter` to start. The first pass steps X in from the start (where the tool touched the work), so e.g. 0.1 mm in steps of 0.1 mm is one pass. Each pass cuts from Mem 1's Z to Mem 2's at the Z speed set (which you can change during the cut, for the passes after), retracts if chosen, returns at full speed, and steps X over towards Mem 2's X (the last step may be smaller, to finish exactly there). If pausing, X is brought back in (if retracted) at the start of the cut, and you press `Enter` for each pass; meanwhile, X can be nudged (`W`/`S`, not the `Alt` nudges), and the next pass steps over from there. Without pausing, pressing `Enter` during a pass pauses once it's done (e.g. to clear swarf; `Enter` again cancels that), then `Enter` continues as usual. A step-over of zero repeats the same cut until stopped: with pausing, nudge in and press `Enter` for each cut. With the current feature set (both its diameter and the work's end), the dialog's start can be **Feature** (its default, unless the tool is at a memory slot): X on the feature's surface, and Z just off the work's end (by `FeatureStartClearance`, 0.5 mm unless set), away from the cut, with Z's distance measured from the work's end. This assumes the feature's diameter runs from the work's end, as when turning down from the end. With `TaperCorrection` set in the config (**EXPERIMENTAL**: see lc.cfg), each cut is made as a tiny taper, to cancel out a taper the lathe turns itself; X is shown as if it weren't moving. While it runs, only `Space` (which stops it), `Esc`, the speed keys and `U` work
* `K` - cut knurling (**EXPERIMENTAL**; tried once on the machine, at 80° on a 17.5 mm bar, with good results): a diamond knurl cut with a single-point tool (e.g. a 90° chamfering tool, or a 60° threading tool), rather than pressed in by a knurling wheel. It cuts two sets of helical grooves of opposite hand, each set like a multi-start thread, locked to the spindle as threading is. Set X as a diameter first (with the tool on the work's surface): the grooves' lead depends on the diameter. The dialog is the multi-pass one (start, Z end, X's infeed as the knurl's depth, and the infeed per pass, with `A` for a constant area as for threading passes), plus the number of **starts** (grooves of each hand) and the **helix angle** (the grooves' angle to Z). The lead is π × Ø ÷ tan(angle): at 45°, the work's circumference, so Z moves fast and the spindle has to turn very slowly. The dialog suggests both, and updates them as the start and depth change, until you type your own (which are then kept, next time too; clear one to have it suggested again). The angle suggested is the smallest whose lead Z can follow with the spindle at `KnurlingSpindleRpm` in lc.cfg (e.g. the slowest your spindle runs: 70 rpm gives about 80° on a 17.5 mm bar), or 45° if that isn't set. The starts suggested space the grooves twice the depth apart, measured across them, which with a 90° tool (whose groove is twice as wide as it's deep) gives sharp diamonds; fewer starts leave flats between the grooves. The dialog shows that spacing: at a steep angle the grooves run nearly round the work, so they're much closer across than round it, and too many starts would just turn the work down. The dialog shows the most the spindle may turn at (Z's maximum speed, less a margin, divided by the lead), and won't accept a lead Z couldn't follow even at 5 rpm (make the angle larger, i.e. the grooves more across the work). On a 10 mm bar at 45°, that's about 25 rpm. In knurling mode the spindle counts as turning down to 5 rpm (rather than 30). (In any mode, the rpm shown is rounded down to a multiple of 10 only from 50 rpm up.) The spindle has to be able to turn that slowly: on a VFD, check its minimum frequency, and (with a pot) the frequency it gives with the pot fully down. `Enter` moves to the start, and `Enter` again cuts. Each pass feeds X in, then cuts every start (each 1/N of a turn further round than the last, for N starts) both ways: Z cuts to the end, which cuts one hand, then straight back to the start with the tool still in, which (with the spindle still turning forwards) cuts the other hand. Rather than in order, each cut starts at whichever of the starts still to cut (that way, in this pass) the spindle comes round to first, so it never waits much more than a turn. So X never retracts, and the Z end needs a relief groove (or to run off the work) for the cut back to start in. Pausing, nudging X while paused and `Enter` during a pass work as for a multi-pass; a pause is between passes, not between starts. Lost encoder pulses stop the passes as for threading passes; choose cut knurling again to start afresh. As with threading passes, each pass takes the spindle's direction from how it has been turning over the last tenth of a second, and every pass must turn the same way as the first; a pass whose start angle the spindle turns away from (e.g. turning backwards) is stopped with a warning, rather than waiting for ever. If the spindle stops part way (e.g. the VFD trips), everything stops, and the warning says why
* `C` - gear cutting (**EXPERIMENTAL**, and not yet tried on the machine; only with `GearCutting = true` in the config, as in lc_mill.cfg, and a rotary table as axis 2, in degrees): cuts a spur gear with a form (involute) cutter, the blank on a rotary table standing vertically, so that it turns about X, and each tooth space is a cut along X. It replaces the old electronicRotaryTable program, and lc_rt.cfg, which only turned the table and waited for each cut to be taken by hand. The dialog asks for the gear's **module** and number of **teeth**, and shows the blank's diameter ((teeth + 2) × module), the angle per tooth, and which of the usual eight involute cutters suits that many teeth. Then X's **start** (where X is, or a memory slot) and **end** (a distance, or a memory slot): both should be clear of the blank, as the table turns there. Then the **depth** (the whole depth, 2.157 × module, unless you type another; it follows the module until you do) and the **depth per pass**, as the depth is fed by hand (the mill's Y and Z have no motors). `Enter` moves X to the start; `Enter` again starts, with the first tooth wherever A is then. Before each pass it pauses for you to feed the depth in (it says by how much); `Enter` then cuts every tooth once, going once round the blank: for each tooth A turns on by 360° ÷ teeth (at A's full speed, `Axis2MaxMotorRpm`), X cuts to the end at its speed, and returns through the slot at full speed. A only ever turns forwards, carrying on round from pass to pass, so its backlash stays taken up the same way; for the first tooth it backs off a degree and comes forwards. After the last pass A turns on round to the first tooth, and its position is put back to where it started (e.g. 0°): its memory slots aren't changed, as whole turns leave them in the same places on the table. `Enter` during a pass pauses after the tooth being cut (e.g. to look at it), and `Enter` again goes on to the next tooth. `Space` stops everything. If you stop it and press `Enter` again, X goes back to the start and then A turns on to the next tooth (if it was stopped between teeth), and the passes start again from there, with the first depth. The teeth stay where they are until you choose a different number of teeth, or zero or set A
